# Announcing cx v0.1

cx v0.1 is the first public release of cx, a productive programming language
for high-performance software: C-like syntax, native code through LLVM, and no
garbage collector. Prebuilt binaries for Linux, macOS
(Apple Silicon), and Windows are on the [releases
page](https://github.com/cx-language/cx/releases), or install with `curl
https://cx-language.github.io/cx/install.sh | bash`. See
[Getting started](./hello-world) for all install paths.

If you write C++, this post is for you. cx keeps what C++ got right and
replaces the rest - and the fastest way to show that is code. (Every cx
snippet below runs in your browser with the play button.)

## You already know most of it

This is a complete cx program. If you can read C++, you can read it:

```cs
void main() {
    var args = List(["build", "--release", "--verbose"]);
    var flags = args.filter(a => a.startsWith("--")).toList();
    println(flags);
}
```

What changes is everything around the code: no header files, no forward
declarations, no build-system archaeology. `cx build` compiles every `.cx` file
in the project into an executable. Modules follow your directories;
dependencies come from Git.

## Errors without exceptions

Parsing a number from a string is something every server does. In C++ it looks
like this:

```cpp {.noRun}
int port = 8080;
try {
    port = std::stoi(text);
} catch (const std::invalid_argument&) {
    return std::nullopt; // or throw further, or -1...
}
if (port < 1 || port > 65535) { /* ... */ }
```

In cx, unparseable input is a null, and out-of-range input is a null.
The type says so:

```cs
int? parsePort(string text) {
    int? port = text.parseInt();
    if port == null || port < 1 || port > 65535 {
        return null;
    }
    return port;
}

void main() {
    println(parsePort("8080")); // 8080
    println(parsePort("99999")); // null
    println(parsePort("http")); // null
}
```

Every type is non-nullable unless marked with `?`, and checks narrow
automatically: after `port == null` is false, `port` is just an `int`.
For richer failures, fallible functions return `Result` values instead of
throwing, and callers handle both cases with `switch`.

## Sum types without the visitor dance

Dispatching on a message shape takes an inheritance hierarchy, or
`std::variant` plus a visitation helper you write yourself:

```cpp {.noRun}
struct Click { int x, y; };
struct Keypress { char key; };
struct Quit {};
using Event = std::variant<Click, Keypress, Quit>;

// ...after defining an `overloaded` helper (not in std).
std::visit(overloaded{
    [](Click c) { std::cout << c.x << "," << c.y; },
    [](Keypress k) { std::cout << k.key; },
    [](Quit) { std::cout << "bye"; }
}, event);
```

In cx it is an `enum` and a `switch`. No allocation, no vtables, and the
compiler checks that every case is handled:

```cs
enum Event {
    Click(int x, int y),
    Keypress(char key),
    Quit,
}

void handle(Event event) {
    switch event {
        case Click:
            println("click at ", event.x, ", ", event.y);
        case Keypress:
            println("key: ", event.key);
        case Quit:
            println("bye");
    }
}

void main() {
    handle(Click(10, 20));
    handle(Keypress('q'));
    handle(Quit);
}
```

## Your C libraries come with you

Rewrites fail when they demand a flag day. cx imports C headers directly -
no bindings to write, no FFI layer to maintain - so one file can go first
and the rest follows when it earns it:

```cs
import "stdlib.h";

void main() {
    println(atoi("42") + 1);
}
```

## Why not Rust? Why not Zig?

If you need guaranteed memory safety, pick Rust: its borrow checker proves
what cx merely checks at runtime. That proof costs lifetime annotations and
time spent satisfying the checker; for non-safety-critical software, cx bets
that debug checks plus sanitizers catch the same bugs with less friction.

Zig is closer in spirit - explicit, C-shaped, no hidden control flow - but
lower-level than cx aims: no method syntax, no string type, errors and
allocation spelled out everywhere. cx sits one level up: a hybrid
low-level/high-level language competing with C++, not with C. The full
comparison is in [Comparison with related projects](./comparison).

## Why not Odin? Why not Jai?

These are the closest relatives: game-first, data-oriented, and allergic to
hidden costs. Three differences matter most.

First, null safety. Every cx type is non-nullable unless marked with `?`,
and checks narrow automatically. Odin leans on `Maybe(T)` with explicit
handling; Jai leaves null to programmer discipline. cx treats a forgotten
null check as a compile error, not a crash.

Second, familiarity. cx reads like C++, with method call syntax, so C++
programmers are productive immediately. Odin deliberately has no methods;
Jai's syntax is its own world. And cx ships the whole toolchain in the box:
build with Git dependencies, a test runner, a language server, and the
playground every snippet on this page runs in.

Third, C reuse without drift. cx imports C headers directly -
`import "foo.h"` and the declarations are there, parsed through the Clang
API. Generated bindings rot when the library updates; a direct import
cannot. Adopt one file at a time next to existing C and C++.

## What is in v0.1

- The core language: null safety, tagged unions, `Result`, generics bounded
  by interfaces, destructuring, named arguments, `defer`, lambdas, slices,
  string interpolation, operator overloading.
- Two backends (LLVM and C), the standard library basics, and `cx build`
  with Git dependencies.
- The `cx-lsp` language server: diagnostics as you type, hover, go to
  definition, completions, find references, semantic highlighting.
- The browser playground: the real compiler frontend as WebAssembly, so
  every example on this site runs with no install.
- Prebuilt Linux (x64), macOS (Apple Silicon), and Windows (x64) binaries,
  installable with the one-line installer or from the [releases
  page](https://github.com/cx-language/cx/releases).

## What is not

v0.1 is an honest starting point, not a finished language:

- Language details may still change before 1.0, and there are bugs.
- Prebuilt macOS binaries cover Apple Silicon only; Intel Macs build from
  source.
- The standard library is still thin, compile-time reflection is future
  work, and C++ interop beyond C headers is a longer-term goal.

The fastest way to help is to try it and [report what
breaks](https://github.com/cx-language/cx/issues), or come talk on
[Discord](https://discord.gg/hsDbW9p).
